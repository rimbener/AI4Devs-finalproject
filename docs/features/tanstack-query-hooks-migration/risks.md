# Risks — tanstack-query-hooks-migration

| # | Risk | Type | Likelihood | Impact | Mitigation |
|---|---|---|---|---|---|
| R1 | Stock `QueryClient` defaults introduce live behavior changes across 7 hooks — a failing read now retries 3× with backoff before the Error state appears, and on web a focused or remounted screen refetches. No component, story or e2e may be edited, so the Playwright suite is the only thing that would catch a resulting regression. | technical | M | M | Deliberately accepted in the story and restated in `spec.md` → Accepted behavior changes. Keep every existing hook test as the regression proof; run the full Playwright suite in `reviews_lead` CI. If a retry delay breaks an e2e timing assumption, prefer a per-query `retry` override in the affected hook over changing the shared client. |
| R2 | Slices 6 and 7 delete `ApiKeyProvider` / `ProfileProvider` from the root `_layout.tsx` render path. `RootValidation` gates the entire app on `useProfile()`, so a mistake there is an app-wide blank screen or an auth-gate flip, not a contained hook bug. | technical | M | H | Merge each provider deletion with its barrel + `_layout.tsx` + app-test-mock removal into one atomic task (task-8, task-9) so the tree never type-checks in a half-removed state. Keep `apps/app-study-buddy/src/__tests__/app/(app)/app-layout-settings.test.tsx` green as the wiring proof, and verify `@s49`/`@s58` (two consumers share one read with no provider) before deleting the provider. |
| R3 | D2's `removeQueries` predicate (`queryKey[0] !== 'auth'`) is the single point of failure for cross-user cache isolation. A future key that starts with `'auth'`, or a renamed session key, silently either leaks the previous user's data or evicts the session mid-flight. | technical | L | H | Land slice 0 first, before any user-scoped entry exists. Cover the predicate with `@s1`–`@s4`, including the same-user token-refresh case that must **not** evict. Document the `'auth'` prefix reservation in `.agents/rules/tanstack-query.mdc` (task-10) so the convention is discoverable. Belt and braces: D1 also scopes the profile and api-key keys by user id. |
| R4 | Timeline is dominated by process, not code: 12 tasks across 9 slices means `reviewer_slice` runs 9 times, and 58 scenarios must each map to a concrete test. | timeline | H | M | Slices 1–5 are contained in `libs/hooks` and follow one repeating shape, so review effort should fall sharply after slice 1 establishes the pattern. ~46 of the 58 scenarios map to **existing tests adapted** (wrap in `QueryClientProvider`, swap synchronous post-`act` reads for `await waitFor`), not new ones; only ~12 are genuinely new. Do not renegotiate slice boundaries mid-run — each is independently shippable, so the work can land incrementally. |
