# Risks — ai-provider-registry-frontend

| # | Risk | Type | Likelihood | Impact | Mitigation |
|---|---|---|---|---|---|
| R1 | **`api-key.service.ts`'s current `catch { throw networkError(); }` actively discards information today** — widening `ApiKeyErrorCode` alone (task-8) does nothing until that blanket catch is replaced, and the replacement changes behavior for *every* existing non-2xx `manage-api-key` response, not just the new one. | technical | M | M | task-8's Done criteria require re-running the full existing `api-key.service.test.ts`/`use-api-key.test.ts` suites, not just adding new `provider_disabled` cases — a regression there fails loudly, not silently. |
| R2 | **Two closed unions widened in the same slice** (`ApiKeyErrorCode`, `GenerationErrorCode`) is exactly where an "unknown provider" response could get accidentally reclassified as `provider_disabled` or vice versa. | technical | M | M | task-10 is a dedicated regression task asserting the *value* of the mapped code for all three unknown-provider call sites (generate/save/remove), not just "no exception thrown". |
| R3 | **`ProviderSelector`/`ModelSelector` drop their i18n-key indirection** (`t(PROVIDER_NAME_KEYS[provider])` / `t(model.labelKey)`) for plain catalog strings (task-4) — any other code path still assuming a `labelKey`/`providerNameKeys` shape would silently render literal key strings instead of failing a type check, if the type change is incomplete. | technical | L | M | task-4's Done criteria explicitly change `LessonGenerationPanelValue.savedProviders` to `{ id, name }[]` and `ModelSelector`'s option shape to a plain `label` — a leftover `t(...)` call on a non-key string is a `check-types` pass but a visible one-line diff in review; task-14's full-workspace `check-types` run is the backstop. |
| R4 | **Seed-fixture drift** — if task-5's pinned fixture (the six providers / thirteen models) diverges from what the backend feature actually seeded, "no regression" tests pass against a fixture that no longer matches production. | technical | M | M | task-5 sources its fixture from the *same* table already published in `docs/features/ai-provider-registry-backend/gherkin-scenarios.md` `@s5` — a single upstream source, not re-typed independently. |
| R5 | **This story ships independently of, but strictly depends on, the backend story's Edge Function responses** (`provider_disabled` at the right HTTP status, `enabled`/`sort_order` columns). | timeline | L | H | The backend story is already `pr_ready` (all 12 tasks done, DoD passed) at the time this spec was authored — verified directly (`docs/features/ai-provider-registry-backend/tasks.md` `phase: pr_ready`) rather than assumed. If it merges after this story, every widened-union task (8/9) degrades gracefully: an unmapped `provider_disabled` renders via each service's existing `generation_failed`/`network_error` fallback, not a crash. |
| R6 | **The "Disabled" indicator's exact placement/copy has no seeded fixture to test against** — today's catalog has zero disabled providers, so task-6/task-7/task-13's tests all construct their own ad hoc disabled-row fixture rather than reusing task-5's (deliberately all-enabled) one. | product | L | L | Each task's Notes call this out explicitly so the implementer doesn't try to force a disabled row into the shared parity fixture (which would break task-5's own "matches today exactly" premise). |
| R7 | **`ApiKeySavedList`'s Replace action on a disabled row is left as an open UX question** (task-6's Notes) — the story's ACs don't say whether Replace should be reachable for a disabled, keyed provider, only that Remove must be. | product | L | L | Left enabled by default (least surprising, matches "no client-side gate beyond what's specified"); flagged for the human/`reviewer_slice` design lens to confirm or override during slice-2 review, not decided unilaterally in code. |
| R8 | **Mutation testing scope** — `.agents/skills/mutation-testing`'s StrykerJS scan roots include every touched lib here (`services`, `supabase-services`, `hooks`, `components`, `study-buddy`), unlike the backend story's `supabase/functions/` gap (see that story's `risks.md` R10). | process/tooling | L | L | No action needed — flagged only for contrast with the backend story so a reviewer doesn't assume the same gap applies here. |
