# Risks — ai-provider-registry-backend

| # | Risk | Type | Likelihood | Impact | Mitigation |
|---|---|---|---|---|---|
| R1 | **No SQL test harness exists in this repo.** `@s1`–`@s9` (schema, constraints, seed parity, RLS, FK integrity) cannot be automated — no runner covers `supabase/migrations/`. | technical | H | H | task-12 authors `tmp/<feature>/verify-provider-registry.sql`, a runnable checklist executed against the linked project after `db push`. Follows the existing manual-smoke precedent (`20260722000000_multi_provider_ai_keys.sql`, prior `risks.md R1/R2/R-enc`). Recorded as a DoD item, not hand-waved. |
| R2 | **Deploy ordering is load-bearing.** If the Edge Functions deploy before `supabase db push`, both functions fail closed on a missing table — every generation and key save breaks. | technical | M | H | Documented in task-12 and both migration headers. Migrations land first, always. Fail-closed (D6) makes the failure loud and immediate rather than silent, which is the intended trade. |
| R3 | **One `update` can disable the whole paid tier.** `update ai_providers set enabled = false where id = 'groq'` also disables platform generation, because `lesson-generation.route.ts` hardcodes `provider: 'groq'` for that route (D14). | product | M | H | Prominent warning comment in the registry migration header (task-1) plus the Studio runbook (task-12). Mitigation is documentation, not code — the alternative (exempting the platform route) would make `enabled` mean two different things. |
| R4 | **Accepted risk (D7 — human override).** A catalog row for a provider with no wired `@ai-sdk` factory passes every check, then fails as an opaque `generation_failed` 502; `manage-api-key` will meanwhile store a valid-looking but unusable key. | technical | L | M | **Deliberately unmitigated in code.** The human explicitly chose this over an SDK-capability guard. Documented in the migration runbook (task-12): adding a provider is **code + DB**, never DB alone. Only reachable by operator misconfiguration; all six seeded providers have factories. |
| R5 | **The RLS policy has no server-side consumer.** Both functions read the catalog with the service-role client, which bypasses RLS (D4), so nothing in this story executes the `select to authenticated` policy. Its only consumer is the paired frontend story. | technical | M | M | task-12's checklist runs the `select` as an authenticated user and as `anon` (`@s6`/`@s7`), so the policy is proven before the frontend story depends on it. Explicit DoD item. |
| R6 | **Cross-story coupling.** The frontend story now owns three things this story's UX depends on: widening `ApiKeyErrorCode` **and** `GenerationErrorCode`, the locale copy for both, and the client-side error mapping (D11/D13) — plus deleting the hardcoded registries and dead locale keys (D15). | timeline | M | M | Frontend story amended and committed by the lead for all three. Until it ships, `provider_disabled` reaches the client as an unmapped code and renders via the generic error fallback — degraded copy, not a crash. Cross-referenced in `spec.md`. |
| R7 | **Seed drift between the migration and the code being deleted.** If a seeded label, vision flag or `sort_order` diverges from today's `AI_MODEL_REGISTRY`, the frontend story regresses visibly with no failing test to catch it. | technical | M | M | The exact expected rows are pinned as a data table in `gherkin-scenarios.md` `@s5` and re-asserted by task-12's script. Verified up front that all four locale bundles already hold byte-identical names, so the i18n-key → literal-string conversion is provably lossless. |
| R8 | **Widening `AiProvider` to `string` removes compile-time safety** across `route.ts`, `validation.ts`, `vision-model.ts`, `types.ts` and `provider-factory.ts`; typos in provider ids no longer fail the build. | technical | M | L | Unavoidable consequence of a DB-driven id (D6). Runtime validation moves to the catalog read: an unknown id yields `null` → `invalid_model` 422 (`@s11`/`@s18`), and the FK (task-2) guarantees no `user_ai_keys` row can name an uncatalogued provider. |
| R9 | **One extra DB round trip per generation and per key save** (D9, no caching). | technical | H | L | Accepted deliberately. A primary-key lookup with a small embedded join is negligible beside a 120 s LLM call and the Vault round trip, and the alternative (a TTL cache) would leave a window where a disabled provider still works — a correctness bug traded for an unmeasurable saving. `@s28` guards against a cache being added later. |
| R10 | **Mutation testing cannot reach any of this feature's actual logic — a pre-existing, repo-wide harness gap, not specific to this feature.** `.agents/skills/mutation-testing/scripts/run-mutation.sh` scopes StrykerJS to changed `.ts`/`.tsx` files physically inside `libs/{services,supabase-services,hooks,components,logging-in-out,activities,study-buddy}/src`. This feature's entire implementation (`supabase/functions/_shared/provider-catalog.ts`, `generate-lesson/_shared/*.ts`, `manage-api-key/{provider,index}.ts`) lives under `supabase/functions/`, which the script never scans, regardless of how thoroughly Jest exercises it via the established relative-path reach-in (`libs/supabase-services/src/services/*.test.ts` → `../../../../supabase/functions/...`). The mutation run correctly reported 0 files in scope → 0 mutants → a vacuous "PASS" (`mutation.md`): this is an honest, non-fabricated result, but it proves nothing about whether the 35 Jest suites / 290 tests / 18 Deno tests actually bite this feature's business logic. The same gap almost certainly applied to the pre-existing `lesson-generation.validation.ts`/`vision-model.ts` before this feature touched them. | process/tooling | H | M | **Not fixed here** — `run-mutation.sh` is a harness script under `.agents/skills/`, and ORCHESTRATOR.md forbids editing harness files inside a feature commit. Flagging for a follow-up harness change (extend the script's scan roots to include `supabase/functions/` alongside each Jest-reachable lib, or add a dedicated Deno-mutation path) outside this feature's scope. Until then, this feature's correctness rests on Jest/Deno test review (all 3 slices individually `reviewer_slice`-approved, plus a clean `reviewer_engineering` full review) rather than mutation proof. |
