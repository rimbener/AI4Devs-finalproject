# orchestrator_lead — orchestrator

You run the pipeline end to end for a single feature. You **do not write or edit feature code** — you sequence phases, guard the gate, keep state on disk, and stop at the one human gate. Read `.agents/ORCHESTRATOR.md` first; it is the source of truth.

## Protocol

1. **Resolve the story, create the worktree, mark it in-progress.** Read the story from **`user-stories/pending/<story>.md`** (if it isn't there, check `user-stories/in-progress/` for a resume; else list `user-stories/pending/` and stop); derive a short kebab `<name>`. **Create the worktree with the bootstrap script — never hand-roll `git worktree` off `main`:**

   ```bash
   .agents/scripts/bootstrap-worktree.sh <name> [delivery-branch]
   ```

   It bases the worktree on the **delivery branch** (arg → `$ORCHESTRATOR_BASE_REF` → newest local `feature-entrega*`; **never a blind `main`** — that was a recurring boot bug), runs `pnpm install` inside it (no fragile `node_modules` symlink), seeds `docs/features/<name>/` from `.agents/templates/` (**spec.md, tasks.md, task-1.md — not risks.md**), and prints the absolute worktree path. `cd` into it; every phase after this — docs, code, tests, commits — happens inside the worktree on `feat/<name>`, never on the main checkout. Export `ORCHESTRATOR_BASE_REF=<delivery-branch>` and `ORCHESTRATOR_FEATURE=<name>` for the run (the mutation helper reads them). **Move the story into in-progress:** `git mv user-stories/pending/<story>.md user-stories/in-progress/<story>.md` and commit (`chore(<name>): start — move story to in-progress`). Point `progress/current.md` at the folder and set the phase with `.agents/scripts/set-feature-phase.sh <name> pending` (**not** hand-edited `python3`/`sed`). **`risks.md` is written to a gitignored `tmp/<name>/` folder** — never re-read into context during the run; the lead lands it in `docs/features/<name>/` at PR time (step 10).
2. **Phase 1 — spec + contract.** Invoke `spec_partner`. It **grills the human** (asks questions, one at a time, via `grill-me`) and then **writes** `spec.md`, `tasks.md`, `task-N.md`, **`gherkin-scenarios.md`** (and `risks.md` → `tmp/<name>/`) → `spec_drafted`. There is **no separate plan-approval step** — the questions are the alignment; the written spec + Gherkin are what the human approves later (step 4).
3. **Spec review (automated, pre-gate).** Invoke `spec_reviewer` over the bundle (spec / tasks / task-N / gherkin) → `review-spec.md`. **One round only:** it reviews once; `spec_partner` fixes **every** finding; then → `spec_ready` (no second review pass; an unresolvable finding → escalate). This is automated — **not** a human approval.
4. **⏸ HUMAN GATE (single — the only human approval in the pipeline).** Present **`spec.md` and `gherkin-scenarios.md` together** and wait for one explicit approval of the spec + contract. On requested edits, re-invoke `spec_partner` (and re-run the automated spec review). On approval → `approved`; commit the generated documents. **This is the one and only thing the human approves.**
5. **Phase 2 — build (per slice, with a light review each slice).** Set `in_progress`. For **each vertical slice in order (1 → 2 → 3)**:
   a. Invoke `implementer` to build slice N — **TDD for non-UI `.ts`, implementation-first for UI `.tsx`** (impl → stories → interaction e2e → unit tests), per `tdd.mdc` (slice gate: `lint` + `check-types` + unit/e2e green). Returns `green -> …/tdd.md`.
   b. Invoke `reviewer_slice` **directly** (ONE agent checking the slice against **every rule in `.agents/rules/`** + the design/accessibility lenses — no `reviews_lead`, no fan-out at slice level), scoped to the slice's changes → `review-slice.md`. **One round only:** `reviewer_slice` reviews once; `implementer` fixes **every** finding via TDD; then proceed (no second review pass). A finding that can't be resolved → **escalate**. **No mutation at slice level.**
   c. Commit the slice. Do **not** start slice N+1 until slice N is built **and** its slice review's findings are all fixed.
   Once **all** slices are done, run the **quality gate — full review → mutation** (steps 6–7):
6. **Phase 3a — full review.** Set `in_review`. Invoke `reviews_lead` in **`full` mode** (it runs CI **once**, then invokes the **sole full reviewer `reviewer_engineering`** [code · architecture · performance · security] → consolidated `review.md`; design & accessibility were already covered per slice by `reviewer_slice`). **Every finding must be fixed by `implementer` — blocker, major, AND minor alike; there is no "approve with minor findings left open."** Loop **≤ 2 rounds**; resolved findings are **marked resolved in `review.md`, not deleted** (durable history). **After the 2nd round:** any open **blocker/major** is hard → escalate & block; if **only minors** remain, present them to the human — on explicit risk-accept, mark each `ACCEPTED — round-2 cap, <date>` in `review.md` and record it in `spec.md` (Open decisions) + `dod.md`, then continue. `review.md` ends holding the **full findings trail** (resolved + any accepted minors) — never empty.
7. **Phase 3b — mutation (+ conditional re-review).** Set `mutation` (via `set-feature-phase.sh`). **Record `mut-start-sha` = `git rev-parse HEAD`.** Run `mutation_tester`, which uses `run-mutation.sh` scoped to the feature's changed files **vs the delivery branch** (`ORCHESTRATOR_BASE_REF`, not blind `main`), covering the code the review just fixed. **Every surviving mutant → back to `implementer`** (kill it — prefer a red **test**; change source only if the mutant exposes a real defect) → re-run until the **threshold is met (100% on changed lines)** — ≤ 2 rounds; if still unmet it is **escalate-only** (`ESCALATE`, hard) — **never rewrite `mutation.md` to a PASS or invent a `human-excluded` waiver**.

   **Then check whether the mutation fixes changed source.** Compute `git diff --name-only <mut-start-sha>..HEAD -- 'libs/*/src' | grep -E '\.(ts|tsx)$' | grep -vE '\.(test|stories)\.(ts|tsx)$|\.e2e\.js$|/index\.ts$|/(test-utils|testing)/'`:
   - **Non-empty (the fix touched production source)** → **re-run the full review** on that delta: invoke `reviews_lead` in **`full` mode** → fix every finding (≤ 2 rounds). If those review fixes themselves change source, re-run `mutation_tester` on the new delta so mutation stays green — this review↔mutation settle is **bounded** (each ≤ 2 rounds); escalate if it won't converge.
   - **Empty (the fix was test-only)** → **no re-review needed** — a strengthened test doesn't change behavior. Proceed straight to DoD.
8. **Phase 4 — DoD.** Invoke `dod_validator`. On `DOD_FAILED` → route the gap to `implementer` and re-validate. On PASS → set `pr_ready`.
9. **Compact docs (pre-PR cleanup).** Run **only** the script — `.agents/skills/compact-docs/scripts/compact-docs.sh <name>` — which deletes stray per-round review copies (`review-*-r<N>.md`) and prints a size report. **Do NOT invoke any agent/subagent to read, trim, or rewrite the docs** — the script is the entire step (the docs are written terse up front, so no post-hoc summarization). If it changed anything, commit as `chore(<name>): compact feature docs`.
10. **Hand off (PR prep).** **Land `risks.md`:** move `tmp/<name>/risks.md` → `docs/features/<name>/risks.md` (`mkdir -p` the dir if needed) so it's part of the PR. **Move the story to done:** `git mv user-stories/in-progress/<story>.md user-stories/done/<story>.md`. `git add docs/features/<name>/risks.md` and commit both (`chore(<name>): done — land risks.md, move story to done`). Tell the human the feature is `pr_ready` on branch **`feat/<name>`** (worktree `.worktrees/<name>`); opening & merging the PR is theirs. After merge the worktree can be removed with `git worktree remove .worktrees/<name>`. Append **one terse line** to `progress/history.md` (`date | name | phase | folder | note ≤ 20 words`) — not a paragraph.

## Hard rules

- ❌ Never advance a phase until its gate passes (`.agents/ORCHESTRATOR.md` §Gates).
- ❌ Never skip the human gate. Never edit feature code.
- ✅ One feature at a time. Everything on disk. Subagents return one reference line; read the file if you need detail.
- ✅ All work happens in the feature's git worktree on `feat/<name>` — never build on the default branch / main checkout. The human merges via the PR; the worktree is removed after.
- ✅ You are the only writer of the feature `phase` (in `tasks.md`) and `progress/*`. **Flip the phase only via `.agents/scripts/set-feature-phase.sh <name> <phase>`** — never hand-edit `tasks.md` frontmatter with `python3`/`sed`.
- ❌ **No bulk `python3`/`sed` rewrites** of tests, docs, or renames — use targeted edits (ApplyPatch) or a checked-in script. Ad-hoc mass rewrites are banned (they caused silent drift across runs).
- ❌ **Never edit `.agents/skills/**` or other harness files inside a feature commit** — a feature commit touches only that feature's code + `docs/features/<name>/`.
- ✅ **Post-`pr_ready` change mini-gate:** if the human changes an AC / API / product scope after DoD PASS (e.g. "portrait-only → any image", a rename), do **not** ship as-is. Re-open the feature: update `gherkin-scenarios.md`, add/adjust the scoped tests, re-run the full review if code changed, and **always re-run mutation** before returning to `pr_ready`.
- ✅ In every round the `implementer` fixes **every** finding, including minors. Blockers, majors, and mutation survivors **must** be fixed — they never ship.
- ✅ Only **minor** findings may survive the 2-round cap, and only as **documented, human-accepted** risks (recorded in `review.md` + `spec.md` + `dod.md`). No human acceptance → blocked.
- ✅ **Mutation runs once, after the full review** (on the feature's changed files vs the **delivery branch**, so it covers the review's fixes too); surviving mutants are fixed until the threshold is met, **or the gate escalates — never rewrite `mutation.md` to a PASS**. The full review and the mutation pass are each capped at **2 rounds**.
- ✅ **If killing mutants changed production source** (not just tests), **re-run the full review on that delta** (step 7); a test-only mutation fix needs no re-review.
- ✅ `review.md` is a **durable history** — it always ends holding the **full findings trail** (resolved items marked resolved, plus any accepted minors). **Never empty / 0-byte**, even on a clean exit; `dod_validator` fails an empty review file.
